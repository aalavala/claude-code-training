Northwind Payments — Merchant Console

Architecture overview · generated from a codebase investigation

1. What the app does

Northwind Payments is a fictional payments company. This app is its merchant console — an internal tool for support and operations staff, not a customer-facing product. It's used to:

  • Look up a payment and issue a refund
  • Work the dispute queue
  • Monitor volume, authorization/capture/dispute rates, and per-merchant activity
  • Issue and manage virtual cards planned — NWP-201

The landing page (/overview, the app root / redirects here) shows headline stats (gross volume, payment count, open disputes and amount at risk), a daily volume chart, and a recent-payments list. From there, /payments, /disputes, and /payouts cover the rest of the nav.

All data — merchants, cardholders, amounts, disputes, card numbers — is synthetically generated. Card numbers use the 4242 test BIN only; nothing here resembles real payment data.

Routing is flat (no (group) folders) and mirrors the top-level nav. API routes live under app/api/**/route.ts. Context itself is layered on purpose across four CLAUDE.md files (repo → exercise → app → per-file rules in .claude/rules/*.md), each narrower than the last.

Conventions worth knowing before editing

  • Money is always an integer in minor units internally; formatted only at the display edge via src/lib/money.ts.
  • Dates are stored/bucketed in UTC; local-time conversion happens only at render, via src/lib/dates.ts.
  • One query builder for payments — everything filters through src/data/queries.ts. A second filter implementation is treated as a defect.
  • Server-side allowlist validation for anything arriving from the client (column names, sort fields, statuses) — never interpolated directly into a query or filename.
  • No database: seed data is generated JSON loaded into memory at boot; writes live only for the dev-server's lifetime.

4. Payments export — end to end

Today's export is a plain browser download with no client-side JS — here's the full chain:

  • src/app/payments/page.tsx — renders the table via queryPayments(). The Export control is just an <a href="/api/payments/export?<current filters>"> — no click handler, no CSV building in the browser. Filters come from src/app/payments/filter-bar.tsx via URL search params.
  • Browser navigates to src/app/api/payments/export/route.ts (GET).
  • The route calls parseFilters() (validates/allowlists query params), then filterPayments() and sortPayments() — all three from src/data/queries.ts, operating over the in-memory Payment[] in src/data/store.ts, with merchant-name lookups via src/data/merchants.ts.
  • The resulting rows go into toCsv(rows) in src/lib/csv.ts, which uses a fixed EXPORT_COLUMNS tuple, formats amounts via formatMoney() from src/lib/money.ts, and escapes cells.
  • The route returns a Response with content-type: text/csv and content-disposition: attachment; filename="<exportFilename()>" — the browser triggers the download natively.

Seams already visible for NWP-101

  • toCsv(payments, columns?) already accepts an optional column list — only the route needs to expose it to the client.
  • The export route bypasses paginate(), calling filterPayments/sortPayments directly — so "scope" today already means all filtered rows, not just the visible page. A "current page" option would need new plumbing.
  • parseFilters() is the existing allowlist boundary — any new column/scope params should validate through it (or an equivalent check in the export route) before reaching toCsv or the filename.
Card last-four ships in every export today with no way to exclude it — the exact gap NWP-101 exists to close.
